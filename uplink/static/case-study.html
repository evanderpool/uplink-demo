Uplink: document answers you can check

A private, self-hosted system that answers questions from an organization's own documents — and refuses to publish any answer it cannot prove came from them.

The problem

Every organization sits on documents that hold real answers — filings, manuals, policies, contracts. Getting those answers out has two failure modes. General-purpose chatbots answer fluently from nowhere in particular: when the answer matters, you can't tell whether it came from your documents or from thin air. And most document-AI services solve that by making you upload everything to someone else's servers — a non-starter for anything confidential.

Uplink is built on a different premise: the documents stay where they are, and every answer must prove where it came from.

The product

Uplink indexes a folder of mixed documents — Markdown, PDF, Word, modern and legacy Excel, CSV — into a single searchable database on the machine that owns them. From there it offers two things:

  • Instant keyword search across every document, with the matching passage highlighted and one click to the original file.
  • Asked-and-answered questions: plain-language questions get plain-language answers, composed only from retrieved passages, with citations that open the exact spot in the exact document.

This public demo runs the same engine against ten years of Apple's annual reports — public SEC filings, in their original Excel format. Ask it about a decade of revenue and margins; click any citation and land on the actual row of the actual filing. The private edition points at your own folder and nothing ever leaves your machine — that difference in trust posture is a deliberate, inspectable deployment fork, not a marketing line.

How answers stay honest

"The answer comes from your documents" is a promise most systems make and none enforce. Uplink enforces it in code, at four points:

  1. Retrieve first. The question runs through ranked search (BM25 over SQLite full-text indexing). The answering model sees only the passages retrieval returned — numbered, with their source coordinates.
  2. Cite by number, not by name. The model doesn't write citations; it picks passage numbers from the list it was shown. The citation coordinates — file, section, position — are copied from the index, never generated. A model cannot cite a document it was never given.
  3. Verify before publishing. Before any answer is shown, every citation is checked against the index. A citation naming a document that isn't there — or one the user deselected — causes the answer to be refused, not displayed.
  4. Say "I don't know" honestly. If retrieval finds nothing relevant, the system says the documents don't cover it. It is built to prefer an honest gap over a confident guess.

Grounding here is a property of the pipeline, not a request in a prompt.

Scoping works the same way: if a user limits a question to specific documents, that selection travels with the question, constrains retrieval, and is re-checked at publication. The checkbox is a contract, and the contract is enforced.

Measured, not claimed

Accuracy claims in this field are usually adjectives. Uplink's are numbers with sample sizes, produced by a repeatable evaluation harness that ships in the repository:

  • Golden question sets — curated questions with known correct source documents — are scored automatically: was the first result correct (hit@1), was a correct one in the top five (hit@5), and how high did it rank (MRR).
  • Every published rate carries its sample size and a 95% confidence interval. A 90% score over ten questions is presented as exactly that — a small sample with a wide interval — because overclaiming is the failure the product exists to prevent.
  • Every run is logged. The evaluation history is a file in the repo; the in-app metrics panel re-scores the live index against the published baseline, so a change that quietly degrades retrieval shows up as drift, with the failing questions named.

How it was built

This project is also a demonstration of a working method. I directed the build; AI coding sessions executed it. The division of labor was strict and it's the reason the pace didn't cost quality:

  • I owned the decisions — the privacy model, what gets verified and how, the scope of every phase, what ships publicly versus stays private, cost ceilings, and the security gates. Each meaningful decision is written down in an append-only decision log.
  • AI sessions owned the keystrokes — implementation, test-writing, and refactoring, working phase by phase against the scope I set.
  • Nothing merged on trust. Every phase landed with automated tests (25 on day one, 343 today) and went through adversarial review passes — dedicated sessions instructed to attack the work, whose findings were fixed and then pinned as regression tests so they can't come back.

Engineering choices worth noticing

  • Radically small dependency surface. The core engine runs on Python's standard library and SQLite — no web framework, no vector database, no orchestration stack. Deployment is "copy the folder." Format readers are optional add-ons that degrade gracefully.
  • A deliberate seam for the answering brain. Questions go into a queue; something answers them through the same verification gate. Locally that's a supervised session; on this demo it's an inexpensive API model. Swapping brains changed no product code — the seam was designed in from the start.
  • Cost designed to a ceiling, not a hope. Free hosting; an answering model that costs about a penny per question; a per-visitor limit of five questions with a three-day reset; and a hard monthly spend cap upstream. The worst possible outcome is "the demo pauses" — never a surprise bill.
  • Security posture by construction. On a private machine, all writes are localhost-only. On the public internet, exactly one write exists — asking a question — and it's rate-limited. Uploads, feedback, and administration simply do not exist on the public surface. The public launch was additionally gated behind a scheduled security review.
